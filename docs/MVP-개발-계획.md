# HURI UP — MVP 개발 계획 (제안)

> 작성일: 2026-11-20 · 근거 자료: 이 폴더의 STEP1~7 문서, 프로젝트 JSON, 페르소나·랜딩페이지 문서

---

## 1. 한 줄 목표

**방석이 없어도 '착석 → 기준 자세 → 기울어짐 → 진동 → 고쳐 앉기' 흐름을 끝까지 체험할 수 있는 웹앱을 만들어 GitHub Pages로 배포한다.**

- 이 MVP로 확인할 것은 기획서의 '가장 먼저 얻어야 하는 결과'입니다. 사용자가 화면을 보지 않고도 자세가 무너진 걸 알아차리고 고쳐 앉는지 봅니다.
- 실제 방석(압력센서·진동 모터)은 아직 없다고 가정했습니다. 그래서 앱 안에 **방석 시뮬레이터**를 넣어 센서 값을 흉내 냅니다. 방석 시제품이 생기면 시뮬레이터 자리에 실제 방석을 끼워 넣을 수 있게 설계합니다.

---

## 2. 왜 이런 방식인가

| 제약 | 그래서 이렇게 |
|---|---|
| GitHub Pages는 **정적 웹페이지만** 올릴 수 있음 (서버·DB 없음) | 서버 없이 브라우저 안에서만 동작하는 웹앱으로 만들고, 기록은 브라우저 저장소(localStorage)에 저장 |
| 방석 하드웨어가 아직 없음 (기획서에 시제품 언급 없음) | 시뮬레이터로 왼쪽/오른쪽 압력을 조절해서 시나리오 전체를 재현 |
| 진동은 방석이 해야 하지만 지금은 방석이 없음 | 휴대폰 진동 + 화면 효과 + 소리로 대신함 (아래 '알려진 한계' 참고) |
| 초보 팀이 함께 고쳐 나가야 함 | 널리 쓰이고 자료가 많은 도구만 사용 |

---

## 3. 기술 구성

| 항목 | 선택 | 이유 |
|---|---|---|
| 화면 | **Vite + React + TypeScript** | 가장 흔한 조합이라 자료가 많고, 빌드 결과를 바로 GitHub Pages에 올릴 수 있음 |
| 화면 이동 | React Router (HashRouter) | GitHub Pages에서 새로고침해도 404가 나지 않음 |
| 저장 | localStorage | 서버 없이 기준 자세·오늘 기록 저장 |
| 테스트 | Vitest | 자세 판단 로직(기울어짐·시간 계산)을 자동으로 검사 |
| 배포 | **GitHub Actions → GitHub Pages** | `main`에 올리면 자동으로 빌드·배포 |
| 이 PC 상태 | git 2.55, Node 26, npm 11 설치됨 · GitHub CLI(gh)는 없음 | gh 없이 git만으로 진행 가능 |

### 코드 구조 (핵심 3층)

```
방석 신호 (CushionSource)        ← 지금: 시뮬레이터 / 나중: 실제 방석(블루투스)
        │  왼쪽·오른쪽 압력 값
        ▼
자세 판단 (PostureEngine)         ← 착석 여부, 기준 대비 기울어짐, 지속 시간, 교정 확인
        │  상태: 대기 / 착석 / 바름 / 기울어짐 / 알림 / 교정됨
        ▼
화면 (6개 페이지)                  ← STEP7 페이지 구조 그대로
```

자세 판단은 화면과 분리된 순수 함수로 만들어 테스트를 붙입니다. 방석이 바뀌어도 이 부분은 그대로 씁니다.

## 4. 만들 화면 (STEP7 기준)

| # | 화면 | 들어가는 기능 | MVP에서 하는 일 |
|:-:|---|---|---|
| 1 | 방석 준비 | 방석 연결 확인 | '방석 연결' 버튼 → 시뮬레이터 방석과 연결됨 표시 |
| 2 | 착석 확인 | **huri up**, 기준 자세 설정 | 앉으면 측정 자동 시작, 바르게 앉아 기준 자세 저장 |
| 3 | 자세 측정 | 실시간 자세 감지 | 현재 상태(바름/왼쪽·오른쪽 기울어짐), 좌우 압력, 착석 시간 표시 |
| 4 | 자세 알림 | 진동 자세 알림 | 기울어진 채 정해진 시간이 지나면 진동·화면 알림 |
| 5 | 교정 확인 | 자세 교정 확인 | 기준 범위로 돌아오면 알림 멈춤, 교정 횟수 +1 |
| 6 | 측정 종료 | 착석 기록 확인 | 일어나면 자동 종료, 오늘 착석 시간·바른 자세 비율·알림·교정 횟수 |

**방석 시뮬레이터**: 모든 화면 아래에 접을 수 있는 패널로 둡니다. [앉기] [일어나기] 버튼과 왼쪽/오른쪽 압력 슬라이더, [왼쪽으로 기울기] [바르게] 같은 빠른 버튼을 넣습니다.

### 기준값 (팀이 정해야 함)

기획서에 '일정 시간'으로만 적혀 있어서, 앱의 설정 화면에서 바꿀 수 있게 만들고 아래 값은 **시연용 임시값**으로만 씁니다.

| 값 | 시연용 임시값 | 비고 |
|---|---|---|
| 기울어짐으로 볼 좌우 압력 차이 | 기준 대비 15%p | 실제 방석으로 측정해 보고 정해야 함 |
| 알림까지 기다리는 시간 | 5초 | 실제 사용에서는 더 길어야 할 가능성이 큼 |
| 착석으로 볼 최소 압력 | 시뮬레이터 기준 값 | 가방·책을 올렸을 때 오감지 여부는 실제 방석으로 시험 필요 (STEP5 불확실성) |

## 5. 개발 단계

| 단계 | 할 일 | 끝났다고 보는 기준 |
|---|---|---|
| **M0 준비** | GitHub 저장소 만들기, 기획 문서를 `docs/`로 옮기기, 아래 6장 '기획 보완' 반영 | 저장소에 기획 문서가 올라가 있음 |
| **M1 뼈대 + 첫 배포** | Vite 프로젝트 생성, 6개 빈 화면과 이동 연결, GitHub Actions 배포 | `https://<계정>.github.io/<저장소>/`에서 6개 화면 이동 가능 |
| **M2 착석·기준 자세** | 시뮬레이터, huri up(착석 감지), 기준 자세 저장 | 시뮬레이터에서 [앉기]를 누르면 측정 시작, 일어나면 중지 |
| **M3 감지·알림·교정** | 자세 판단 로직 + 테스트, 진동 알림, 교정 확인 | 기울인 채 설정 시간이 지나면 알림, 바르게 하면 알림이 멈추고 교정 횟수 +1 |
| **M4 기록·상태 처리** | 오늘 기록 저장·표시, 모든 화면의 빈 상태·오류 상태 | STEP7의 빈/오류 문구가 실제로 나타남 |
| **M5 다듬기·검증** | 휴대폰 화면 맞춤, 설정 화면, README·시연 방법 작성 | 휴대폰으로 배포 주소를 열어 시나리오 7줄을 끝까지 재현 |

M1에서 먼저 배포까지 연결합니다. 그러면 이후 단계마다 바로 팀원과 결과를 확인할 수 있습니다.

### MVP 이후 (지금은 하지 않음)

- **실제 방석 연결**: 압력센서(FSR)와 진동 모터를 단 ESP32 같은 보드를 블루투스(Web Bluetooth)로 연결합니다. 코드 구조상 `CushionSource`만 새로 만들면 됩니다.
- **랜딩페이지**: `07-랜딩페이지.md` 기반. 아래 주의사항을 해결한 뒤 진행합니다.
- **기간별 기록·리포트**: 7일 리포트, 학부모 공유 등 (페르소나 문서의 아이디어)

## 6. 개발 전에 고쳐야 할 기획 내용

1. **'지금 반드시 구현' 기능이 huri up 하나뿐입니다.** 화면 6개에 필요한 기능을 기능 목록에 추가해야 합니다. 추가할 기능은 방석 연결 확인, 기준 자세 설정, 실시간 자세 감지, 진동 자세 알림, 자세 교정 확인, 착석 기록 확인입니다.
2. **huri up은 '지금' 단계인데 '핵심 필수: 아니오'로 되어 있습니다.** 착석 감지 없이는 측정이 시작되지 않으므로 필수로 바꾸는 것을 권합니다. 이름도 기능 이름(예: '착석 자동 감지')으로 바꾸는 게 좋습니다.
3. **'착석 확인' 화면의 오류 상태에 다른 화면 내용이 섞여 있습니다.** `[다시 연결] 버튼a진동 알림 발생 표시, 기울어진 방향…` 부분은 '자세 알림' 화면에서 잘못 붙여 넣은 것으로 보입니다.
4. **화면 이름 끝에 공백이 있습니다.** '방석 준비 ', '착석 확인 '은 링크 이름이 어긋나지 않게 공백을 지웁니다.
5. **앱 연결 여부가 문서끼리 다릅니다.** '방석 준비' 화면은 앱 연결을 전제로 하는데, huri up은 '앱 연결 없이도 작동'을 목표로 합니다. 방석 혼자서도 진동을 줄지 정해야 합니다.
6. **제품 이름이 HURI UP, HURRY UP, '이름 없는 프로젝트'로 섞여 있습니다.** 하나로 정해야 저장소 이름과 앱 제목을 정할 수 있습니다.

### 랜딩페이지 관련 주의

`07-랜딩페이지.md`에는 '체험단 30명 실측', 학생·학부모 후기 섹션이 있습니다. 그런데 STEP2 기준으로 사용자 조사는 아직 **계획 단계**입니다. 실제 데이터와 후기가 생기기 전에는 이 내용을 실제처럼 공개하면 안 되고, '예시' 자리표시로만 둬야 합니다.

## 7. 알려진 한계 (웹 MVP라서 생기는 것)

| 한계 | 영향 | 대응 |
|---|---|---|
| **아이폰(Safari)은 웹페이지에서 휴대폰 진동을 쓸 수 없음** | 아이폰에서는 진동 알림이 안 울림 | 화면 깜빡임 + 소리로 대신하고, 화면에 안내 표시 |
| 휴대폰 웹페이지는 화면이 꺼지거나 다른 앱으로 가면 멈춤 | STEP7의 '앱은 백그라운드에서 측정'은 웹으로는 불가능 | 측정 중에는 화면 꺼짐 방지(Wake Lock) 사용, 앱을 켜 둔 상태로 시연 |
| 시뮬레이터는 진짜 압력이 아님 | 감지 정확도는 검증할 수 없음 | 이 MVP는 **흐름과 진동 알림 수용성** 검증용이고, 정확도는 하드웨어 단계에서 검증 |
| 기록이 브라우저에만 저장됨 | 기기를 바꾸면 기록이 사라짐 | MVP 범위에서는 허용 |
| Web Bluetooth(나중 단계)도 아이폰 Safari 미지원 | 실제 방석 연결 단계에서 아이폰 사용자는 별도 방법 필요 | 하드웨어 단계에서 다시 결정 |

## 8. 시작 전에 정할 것

1. **GitHub 계정과 저장소 이름** (예: `huri-up`). 무료 계정으로 GitHub Pages를 쓰려면 저장소를 **공개(public)**로 해야 합니다.
2. **방석 시제품이 지금 있는지.** 있으면 M3 이후 실제 방석 연결을 앞당길 수 있습니다.
3. **6장의 기획 보완을 누가 할지.** 기획 도구(JSON)에서 직접 고칠지, 저장소의 `docs/` 문서에서 고칠지 정합니다.
